Executive Summary

Problem Overview

Rotating Savings and Credit Associations (ROSCAs) are informal, peer-to-peer financial tools used by over a billion people globally—particularly small business owners in emerging markets—to pool capital and secure interest-free credit. However, traditional ROSCAs suffer from systemic vulnerabilities:

  • Defaulter Counterparty Risk: If a member defaults early in the cycle, the savings circle collapses, leaving subsequent members empty-handed.
  • Capital Inefficiency: Web3 protocols mitigate default risk by requiring 100% to 150% over-collateralization. This approach is counterproductive for SMEs seeking access to capital they do not already have.

Roda's Solution

Roda is an on-chain collaborative savings protocol deployed on Arc Network. We replace heavy collateral locks with smart contract escrow structures, automated deficit recovery rules, and an autonomous, off-chain risk validation engine: the AI Liquidity Guardian.

Roda establishes a transparent, reputation-backed credit history (using ERC-8004 registries) that dynamically adjusts the required security deposits as users demonstrate positive repayment behaviors.

Arc Network and Stablecoin Integration

SME micro-savings require high-frequency, low-value contributions. Standard L1 networks are economically unviable due to high gas costs. By building on Arc L1, Roda benefits from USDC-native gas fees and sub-second deterministic finality. This keeps recurring micro-contributions cost-efficient, ensuring gas fees do not erode user savings.

Technical Innovation & Architecture

Implemented Protocol Features

1. Dynamic Collateral Withholding

Within the closeRound() logic of SavingsCircle.sol, the contract calculates the beneficiary's remaining liability to the pool. When a circle is initialized, members deposit a baseline security collateral. Upon winning a payout pot, the contract evaluates if the beneficiary's locked collateral covers their remaining round duties. If it does not, the contract automatically retains the difference from their gross payout and locks it as collateral to secure the remaining members against late-cycle default.

2. Late Default Deficit Protection

If a member exhausts their collateral and defaults, Roda does not freeze the circle. The contract records the shortfall as an on-chain debt entry. When the defaulter's payout round arrives, the contract automatically intercepts the payout pot, clears the outstanding debt, and sends the recovered funds to replenish the accounts of the members who suffered shortfalls in prior rounds.

3. ERC-8004 Credit Registry

Every successful contribution and repayment updates the user's reputation profile via the ReputationRegistry (ERC-8004). This ledger dynamically decreases the collateral requirement for future savings circles, transitioning users from collateral-backed to reputation-backed borrowing.

4. Dual-Wallet Validator Architecture

To comply with the ReputationRegistry (ERC-8004) self-reporting restrictions (which revert if an agent owner wallet attempts to report reputation scores directly on its operations), we implemented a dual-wallet security design. The primary owner wallet (AI_AGENT_WALLET_ID) handles liquidity management and transaction execution, while a separate validator wallet (AI_AGENT_VALIDATOR_WALLET_ID) submits feedback logs to the ReputationRegistry. This ensures compliance with registry rules while keeping reporting completely decoupled.

The Agentic Economy & Circle Integration

AI Liquidity Guardian

In Roda, risk management is automated through the AI Liquidity Guardian. Triggered via the client application, the server-side validation agent queries the smart contract via RPC to inspect the member's risk profile:

  • Currently locked collateral balance
  • Outstanding defaults and cumulative debt
  • Historical payment behaviors (payment vs. default status per round)

Off-Chain Simulation Layer: L2 Agent Network

To model high-volume transactions and show how Roda scales beyond L1 constraints, we implemented a deterministic L2 Agent Network. This layer models high-frequency off-chain micro-payments and state channels among 378 simulated agent wallets. It runs on a deterministic client-side simulation, demonstrating how agent-to-agent nanopayments are batched and periodically settled back to Arc L1.

Autonomous On-Chain Injection

The Guardian agent runs a credit evaluation and outputs a structured risk assessment. If a member's risk profile is within acceptable limits, the backend triggers an autonomous transaction injection using Circle's Developer-Controlled Wallets API. The agent's wallet deposits the contribution amount on behalf of the member, protecting the pool's liquidity and preventing unnecessary defaults.

Circle & Arc Product Feedback

Why We Chose Circle & Arc

ROSCAs require high-frequency, recurring micro-contributions (typically $10–$50) where standard EVM gas fees (often $0.20 to $1.50) make participation economically unviable. Arc’s sub-second finality and native USDC gas fees allow micro-deposits to retain 99.9% of their value on-chain. Furthermore, using USDC as the native gas token eliminates currency volatility risk for autonomous agents (such as our AI Liquidity Guardian), allowing the risk engine to budget execution fees deterministically without managing floating gas token prices.

Developer Experience Gaps & Feedback

What Worked Well

  • Sub-second Finality: Confirmation times under one second on Arc Testnet match the speed of Web2 banking interfaces.
  • Native USDC Gas: Eliminating volatile gas token management simplifies fee calculations and treasury operations.
  • Developer-Controlled Wallets: The MPC API makes automating on-chain operations for autonomous agents straightforward.

What Can Be Improved

  • Lack of Pre-deployed Multicall3 Contract: Arc Testnet currently lacks a pre-deployed Multicall3 contract at the standard address (0xcA11bde05977b3631167028862bE2a173976CA11). Since standard React frontends built on Wagmi/Viem use multicall contracts to bundle read-queries, batch reads failed out of the box. We had to write a client-side parallel promise wrapper (multicallSafe) to bypass this, which increases RPC calls and code complexity.
  • ERC-8004 Registry Self-Feedback Reverts: The ReputationRegistry contract reverts self-feedback transactions to prevent sybil manipulation. This requirement was not explicitly documented, necessitating a dual-wallet validator design (Owner vs. Validator wallet) to successfully write logs. Clearer documentation of these registry constraints would save builders significant debugging time.

Recommendations

  1. Pre-deploy Multicall3 at the standard address (0xcA11bde05977b3631167028862bE2a173976CA11) on Arc Testnet.
  2. Provide official SDK helper templates or examples for multi-wallet autonomous agent validation patterns to greatly streamline development for agentic economy use cases.
